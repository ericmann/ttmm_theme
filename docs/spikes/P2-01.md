# P2-01 spike: export term definitions, Playground import and CLI server shape

## Question

(1) In the wp-env `cli` container, does `wp export --post_type=post,page,attachment` (and the
variants `--post_type=post --post_type=page`, no filter) emit `<wp:category>`/`<wp:tag>`/
`<wp:term>` definitions with `<wp:termmeta>` for `series` and category descriptions? Which
invocation does?

(2) Does `npx @wp-playground/cli server --blueprint=<file> --port=<p> --login` (v3.1.x) fetch
`url` resources from a `node:http` server on `127.0.0.1`? Is the `importWxr` key
`fetchAttachments` valid in the schema, or does the default importer fetch attachments anyway?

(3) After `importWxr` of a two-item hand-made WXR (one post with a term carrying `ttm_status`/
`ttm_form` term meta and one attachment), does the term meta exist (`wp term meta list`
equivalent)?

(4) Cold boot + import wall time (for CI).

## Method

All commands run against the flight's own wp-env (`npx wp-env start`, WP 7.1.1) and against
`@wp-playground/cli` 3.1.55 (`npx --yes @wp-playground/cli --version`).

**Q1** — three exports via `npx wp-env run cli -- wp export --stdout --skip_comments [...]`,
redirecting stdout and stderr to separate files so PHP deprecation notices (this WP-CLI phar
logs several under PHP 8.3) don't pollute the XML:
- `--post_type=post,page,attachment`
- `--post_type=post --post_type=page` (WP-CLI only keeps the last `--post_type` flag; not run
  separately since the single-flag CSV form above already answers the filtered case)
- no `--post_type` at all

Each output was grepped for `<wp:category>`, `<wp:tag>`, `<wp:term>` and `<wp:termmeta>`.

**Q2/Q3** — a `node:http` static file server (plain `node:http`, no dependency) on
`127.0.0.1:8791` serving a hand-built two-item WXR (`spike.xml`: one `wp:term` with two
`wp:termmeta` rows, one `post` item referencing it via `<category>`, one `attachment` item with
a `wp:attachment_url` pointing at a 1x1 PNG on the same server) plus the PNG itself. A blueprint
(`--blueprint=blueprint.json`) ran `importWxr` against `http://127.0.0.1:8791/spike.xml` with
`fetchAttachments: true`, then two `wp-cli` steps. `@wp-playground/cli server
--blueprint=... --port=<p> --login --verbosity=debug` was run with a timeout and polled for
`Ready!`/errors. Findings on term meta were confirmed by mounting a host directory
(`--mount=/host/out:/out`) and having a `wp-cli` step run `wp eval "file_put_contents('/out/....
json', wp_json_encode(get_term_meta(...)))"`, since **a successful `wp-cli` step's stdout is not
echoed to the CLI's own console at any `--verbosity` level** (only a failing step's stdout/
stderr is printed) — this ruled out reading `wp term meta list`'s own output directly and forced
the mount+`wp eval` approach. Attachment delivery was checked two ways: the static server was
given a one-line access log, and the imported site's own `?rest_route=/wp/v2/media` was queried
with a cookie jar (`-c`/`-b`) after following the `--login` redirect chain (`curl -s -L`).

Note: the first hand-built WXR used a custom `series` taxonomy, which doesn't exist on a bare
Playground boot (no `ttm-core` plugin installed in this quick spike) — `wp term list series`
failed with "Taxonomy series doesn't exist." The taxonomy was switched to WordPress's built-in
`category` for the experiment; this only proves generic-taxonomy term-meta import (sufficient to
answer Q3 — the importer's term-meta handling isn't taxonomy-specific), not that `ttm-core`'s
`series` taxonomy itself is registered before import in the real flight blueprint (P2-04's own
blueprint already installs the plugin before `importWxr`, so this doesn't apply there).

**Q4** — timed one clean boot+import of the two-item WXR (`date +%s.%N` before spawn, polling
the log for `Ready!` every 2s) with the WP release already cached by an earlier run in the same
session (this machine's XDG cache, not measured cold).

## Findings

**Q1 — `wp export` never emits `<wp:termmeta>`, in any invocation.**

| invocation | `<wp:category>`/`<wp:tag>`/`<wp:term>` count | `<wp:termmeta>` count |
|---|---|---|
| `--post_type=post,page,attachment` | 0 | 0 |
| no `--post_type` filter | 47 | 0 |

With a `--post_type` filter, WP-CLI's exporter skips term definitions entirely (only posts/pages/
attachments are written, no `<wp:term>` blocks at all — the seeded `series` term descriptions
and everything else about taxonomies is gone). Without a filter, all 47 terms across every
taxonomy (`category`, `post_tag`, `series`, `nav_menu`, …) are written with their descriptions,
but grepping the bundled `wp-cli/export-command` phar itself for `termmeta`/`wp:termmeta` found
**no matches anywhere in the WP-CLI binary** — this WP-CLI version's WXR exporter has no term-meta
support at all, independent of flags. This contradicts the SPEC §6.3 assumption that `wp export`
carries `series` term meta (`ttm_status`/`ttm_form`) end to end; `wp export` only ever emits
`term_id`/`taxonomy`/`slug`/`parent`/`name`/`description`.

**Q2 — the local `127.0.0.1` static server works for the WXR file itself, but Playground's
`importWxr` never requests the attachment binaries from it.**

The `url`-resource fetch for the blueprint step's own `file` (the WXR at
`http://127.0.0.1:8791/spike.xml`) succeeded on the first request logged by the static server —
confirming `@wp-playground/cli server`'s networking (`features.networking: true`) can reach a
`node:http` server on loopback for the primary resource fetch. `fetchAttachments` **is** a valid
schema key (`blueprint-schema.json` → `ImportWxrStep.fetchAttachments`, boolean, `default: true`)
so the SPEC/PLAN's assumption there is correct. But across three separate boots with
`fetchAttachments: true` (the schema default, and set explicitly), the static server's access log
never showed a second request for `/images/demo-test.png` — Playground's WXR attachment importer
did not attempt to download it at all, and `?rest_route=/wp/v2/media` on the booted site
consistently returned `[]`. The post itself imported correctly (`?rest_route=/wp/v2/posts`
returned the `Spike Post` item with its original id 1001 retained), and its `_thumbnail_id`
postmeta pointing at 1002 imported too, but no attachment post was ever created for it.

**Q3 — term meta survives `importWxr` intact.**

`get_term_meta(<imported category id>)` on the booted site returned
`{"ttm_status":["in-progress"],"ttm_form":["nonfiction"]}` — an exact match for the two
`wp:termmeta` rows on the hand-built WXR's `wp:term`. So *if* term meta is present in the WXR fed
to `importWxr`, Playground's importer preserves it faithfully; the gap is entirely upstream, in
`wp export` never writing it in the first place (Q1).

**Q4 — measured boot time.**

One clean boot + `importWxr` of the two-item WXR, WP release already present in this machine's
Playground cache from an earlier run in the same session: **~46 seconds** to `Ready!`. The very
first boot in this session (cold WP-release cache, first `npx --yes` also resolving the CLI
package) took closer to 90 seconds. CI runners start with an empty cache every run, so budget for
the cold-cache case (`PLAYGROUND_BOOT_TIMEOUT_MS` in the PLAN's `check.mjs` design is already
600000ms / 10 minutes, which comfortably covers either figure).

## Decision

- **Export command** — `build.mjs` cannot get term meta from `wp export` at all (Q1), so it must
  not rely on the WXR exporter for it. Use the **no-filter** `wp export --stdout --skip_comments`
  form (keeps every term's name/slug/description, matching the PLAN default "no `--post_type`
  filter... so term definitions... are included") and have `normalizeWxr`/`build.mjs` **inject**
  `<wp:termmeta>` blocks for the `series` taxonomy's terms itself, synthesized from a direct
  `wp term meta list <id> --all --format=json` (or `wp eval`) read per series term *after* the
  XML export, keyed by the term's slug so renumbering in `normalizeWxr` still lines up. This is a
  necessary correction to the PLAN's "Export mechanics" decision, not an implementation of it as
  written — P2-02/P2-03 must budget for this extra step rather than assuming `wp export` alone
  carries `ttm_status`/`ttm_form`.
- **Server command line** — `check.mjs` uses `npx @wp-playground/cli server
  --blueprint=<tmp>/blueprint.local.json --port=<ephemeral> --login`, exactly the PLAN's assumed
  form; the local `node:http` static server on `127.0.0.1` is confirmed reachable for the
  blueprint's own resource fetches.
- **`fetchAttachments`** — keep the key in the template (it's schema-valid and defaults to
  `true`), but **do not rely on it working against the local check's `127.0.0.1` image server**
  (Q2): it silently fetched zero attachments in every run of this spike. P2-06's
  `check-assertions.mjs` must not assert on an actual attachment/media object existing after the
  local-variant `importWxr`; asserting on the **post's own `<img src="...">` markup** (already the
  plan for `.ttm-lead-story img`/`.wp-block-post-featured-image img` `src` containing `demo-`) is
  unaffected, since that only needs the post content's `<img>` tag to parse correctly, not a real
  Media Library attachment row. The *real* (non-local, `demo:check` without `--url`) Playground
  run imports from the actual `raw.githubusercontent.com` WXR/image URLs, which is a different,
  real-internet host — this spike's finding is specific to a bare loopback address and does not
  by itself prove or disprove whether the public-host case fetches attachments; P2-06 should
  re-verify against the real host once it exists and fall back to the same img-src-only
  assertion strategy if it also comes up empty there.
- **Blueprint steps beyond §6.4** — no extra steps found necessary from this spike beyond the
  PLAN default (`wp site empty --yes` before `importWxr`); term meta itself needs no extra
  blueprint step once it's present in the WXR (Q3).
- **Measured boot time** — ~46s warm, ~90s cold-ish in this session; well inside the planned
  600000ms `PLAYGROUND_BOOT_TIMEOUT_MS`.

## Playground result (P2-07)

Whether series term meta and category descriptions arrived through `importWxr`, against the
*real* build (107 posts, 13 attachments, 7 series), and which blueprint steps were needed to
restore derived state:

- **Category descriptions**: yes, unconditionally — `wp export`'s no-filter form keeps every
  `<wp:category>`'s `<wp:category_description>`, and `normalizeWxr()` never touches it;
  `importWxr` preserves it (categories aren't affected by the termmeta gap below).
- **Series term meta**: **not** through `importWxr` alone — confirmed for real (not just this
  spike's two-item fixture) that `wp export` never writes `<wp:termmeta>`, so every series term in
  the actual `.github/demo-content.xml` had none until P2-06 added an explicit fix: `build.mjs`
  reads each series term's `ttm_status`/`ttm_form` directly via `wp eval` after seeding, and
  `normalizeWxr()` injects it into the corresponding `<wp:term>` block. Evidence: before that fix,
  `demo:verify` (inside the blueprint) failed with `missing term meta: <slug>` for all 7 series,
  every time, regardless of content volume; after it, `demo:verify` passes.
- **Blueprint steps needed to restore derived state, in practice** (beyond the §6.4/PLAN
  default): the six post-import `wp-cli` steps (`wp rewrite structure`, `wp ttm primary:assign`,
  `wp ttm recount --all`, `wp ttm series:rebuild`, `wp ttm stats:flush`, `wp ttm demo:verify`) had
  to be consolidated into **one** `wp-cli` step running `wp eval` with all six operations inlined
  as direct calls to the same command classes. Real headless Playground hits a hard
  `memory access out of bounds` WASM trap by roughly the ninth separate `wp-cli` blueprint step in
  a single boot — confirmed independent of which command runs there (removing `series:rebuild`
  moved the crash to `stats:flush` at the same step position) and independent of content volume
  (reproduced with 0, 30 and 124 WXR items). This is a genuine `@wp-playground/cli` 3.1.55
  limitation, not a bug in any of these commands individually (each runs fine standalone against
  wp-env's real MySQL-backed PHP). A `wp_cache_flush()` call was also needed at the end of that
  combined step for `series`/`writing` to serve at all (200 instead of a stale/empty response) —
  Playground boots with a persistent Redis object cache enabled by default, and directly-run PHP
  changes to derived data didn't reliably invalidate it for the request-serving workers otherwise.
- **Still unresolved**: even with the above, the real headless Playground boot's served pages show
  incomplete dynamic content (the article page 404s; the front page's lead photo, series strip and
  the writing page's serial hero render empty) despite `demo:verify` passing inside the same boot —
  this does not reproduce against the real seeded wp-env site (`demo:check --url` is fully green).
  Time-boxed out of P2-06/P2-07; recorded here for whoever picks this up next. Candidate causes not
  yet ruled out: `WP_Query`/rewrite-rule behaviour differences under Playground's SQLite database
  integration versus real MySQL; a caching layer (the same Redis object cache above, or a
  transient) still serving pre-import state to the first few real page requests; or a genuine
  timing race between the worker pool accepting requests and the blueprint's own step sequence
  finishing. `npm run demo:check` in CI (P2-07) may therefore fail on this specific gap; `--url`
  mode against a real site remains reliable.
