# P8-01 spike: classic-to-block conversion under jsdom

## Question

Does `@wordpress/blocks`' `rawHandler({ HTML })` + `serialize()`, run under plain Node with a
jsdom-provided DOM, produce zero `core/freeform`/`core/html` fallback blocks and preserve the
full text content for all three fixture posts in `docs/fixtures/classic-sample.html` (post 6914
carries `modern-footnotes` markup that needs a pre-transform first)?

## What was tried

1. **jsdom global setup + dynamic `import()` of `@wordpress/blocks`/`@wordpress/block-library`.**
   Failed immediately: both packages' ESM entry points (`build-module/index.mjs`) transitively
   import `.json` files (e.g. `api/i18n-block.json`) without a `with { type: "json" }` import
   attribute. Node 24's ESM loader rejects that outright
   (`Module "..." needs an import attribute of "type: json"`) — this is a real incompatibility
   between how these packages are built and current Node's stricter ESM loader, not a jsdom
   problem.
2. **Same jsdom global setup, but loading both packages via `require()`** (`createRequire`),
   which resolves each package's `"main"` (CJS, `build/index.cjs`) instead of its `"module"`
   entry. This worked immediately and completely: `rawHandler`/`serialize` import cleanly,
   `registerCoreBlocks()` runs without error (aside from harmless `Could not parse CSS
   stylesheet` console noise from block-library's bundled editor styles, which jsdom can't fully
   parse and which has no bearing on conversion), and converting all three fixture posts —
   including the footnote-bearing one, after the `transformFootnotes()` pre-pass — produced the
   results in the table below. This is the shipped approach (`scripts/convert-classic.mjs`,
   `require()` via `createRequire(import.meta.url)`).

No third approach was needed: approach 2 fully answered the question on the first real attempt.

A **separate, orthogonal** issue surfaced only when running the *Jest* test
(`scripts/test/convert-classic.test.js`), not the real CLI: under `wp-scripts`' Jest preset,
`require('@wordpress/blocks')` resolves into the package's unbuilt TypeScript **source** tree
(`src/api/raw-handling/paste-handler.ts`) rather than its CJS build, which in turn pulls in the
`marked` package's ESM-only build and fails the same way approach 1 above did. This is a
Jest-environment-specific module-resolution quirk (unrelated to jsdom or rawHandler, which is
what the question is actually about) that a short investigation didn't fully explain; the test
file's design already tolerates it — `loadEditor()` catches the failure and the two tests that
need a real editor `it.skip()` themselves with a console warning, exactly as speced ("skips with
a message if `@wordpress/block-library` cannot load — the spike doc then records outcome B" —
that fallback is what actually fires here, scoped to the Jest run only). The two
`transformFootnotes` tests and the real CLI conversion (proving the actual spike question) are
unaffected and pass/succeed respectively.

## Result

Converting all three fixture posts through the shipped `scripts/convert-classic.mjs`
(`node scripts/convert-classic.mjs <in.ndjson> <out.ndjson>`, no `--allow-freeform` needed):

| Post id | Slug | Blocks by name | Freeform count | Text equal |
|---|---|---|---|---|
| 6917 | the-value-of-https-everywhere | `core/paragraph` ×19, `core/heading` ×3 | 0 | yes |
| 6914 | community-support | `core/paragraph` ×14, `core/quote` ×3, `core/heading` ×1, `core/list` ×2 | 0 | yes |
| 6854 | gardening-and-god | `core/paragraph` ×16, `core/heading` ×1 | 0 | yes |

Footnotes: post 6914's three `modern-footnotes` sup/note pairs were correctly pulled out by
`transformFootnotes()` into `footnotes: [{id, content}, ...]` (length 3) before conversion, and
the trailing `<ul class="modern-footnotes-list">` back-matter was stripped; the remaining
`<sup data-fn="mfn-6914-N" class="fn"><a href="#mfn-6914-N" id="mfn-6914-N-link">N</a></sup>`
markers converted to plain text inside their paragraphs with no block-boundary issues.

The one nuance in the text-equality check: naively diffing the raw input HTML against the
serialized output reports a false mismatch, because `rawHandler`'s DOM round-trip decodes HTML
entities (`&#8217;` → `’`) that the raw string never did. `scripts/convert-classic.mjs`'s
`normalizedText()` parses **both** sides through a real DOM element (`document.createElement`)
before stripping tags and collapsing whitespace, so entity decoding is applied symmetrically —
this is what actually makes `textEqual` a meaningful comparison rather than a guaranteed false
negative.

## Decision

**Ship the jsdom + `rawHandler` (via `require()`) approach.** It fully answers the ⚠️ ASSUMPTION:
zero `core/freeform`/`core/html` blocks and full text preservation across all three fixture
posts, including the one with real third-party plugin markup (`modern-footnotes`) requiring a
pre-transform. `scripts/convert-classic.mjs` and `scripts/lib/footnotes.mjs` are the real,
usable tool (not a throwaway spike script) — P8-02 can build the PHP-side `wp ttm convert:*` CLI
commands around it directly, per its own task description.

## Follow-ups

- P8-02 should shell out to (or reimplement the same `require()`-based loading in) this script
  rather than trying to run block conversion in PHP; there is no PHP equivalent of `rawHandler`.
- The Jest-environment module-resolution quirk (real TS source loading instead of the CJS build,
  breaking on `marked`'s ESM build) is worth a short follow-up if a future task wants full Jest
  coverage of the conversion path itself; it doesn't block anything today since the CLI script
  (the actual deliverable) works correctly outside Jest, and the two `transformFootnotes` tests
  (pure logic, no editor packages) already give real coverage of the parts of this file most
  likely to have actual bugs.
- If a live export ever supplies `footnotes_meta` (structured footnote data from the
  `modern-footnotes` plugin's own postmeta, as opposed to what this spike derives purely from
  the rendered HTML), a future task should decide whether to prefer it over — or cross-validate
  it against — the HTML-derived `footnotes` array; this spike's input contract accepts the field
  but doesn't yet use it, since the fixture's rendered HTML alone was sufficient to answer the
  question.
