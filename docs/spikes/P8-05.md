# P8-05 spike: Jetpack Social share URLs to `ttm_syndication`

## Question

Which Jetpack Publicize/Jetpack Social post meta keys carry the actual mirror URL of a shared
post (as opposed to merely a "this was shared" flag), and in what shape, so
`wp ttm migrate:syndication` can populate `ttm_syndication` from them without ever calling
`unserialize()` directly (rule 15)?

## Keys examined

There is no live Jetpack export available in this environment (no site access, per the flight's
standing constraints), so this spike is based on Jetpack's own published source
(`projects/packages/publicize/`) and the three keys named in SPEC Q-M4/the task text:

1. **`_publicize_done_external`** — written by
   `Automattic\Jetpack\Publicize\Publicize::save_publicized_post_status()` (and the REST
   `jetpack/v4/social/... ` write paths) whenever a Publicize connection reports the URL of the
   resulting mirror post. Shape: `{ service_slug: { connection_id: mirror_url, ... }, ... }`, e.g.
   `{"twitter": {"12345": "https://x.example/1"}, "mastodon": {"67": "https://mastodon.example/2"}}`.
   This is the **only** one of the three keys that carries a URL at all.
2. **`_wpas_done_{service}`** (e.g. `_wpas_done_twitter`) — the legacy (pre-Jetpack-Social-rename)
   per-service "already shared" flag. In Jetpack's own source this is written as a plain boolean
   `1`, never a URL. It answers "was this shared to this service", not "where did it land".
3. **`jetpack_social_post_already_shared`** — a newer, single boolean flag ("has this post been
   auto-shared at all"), also never a URL.

## Shapes observed / expected

| Key | Shape | Carries a URL? |
|---|---|---|
| `_publicize_done_external` | `array<string, array<int\|string, string>>` | Yes |
| `_wpas_done_{service}` | `bool` (`1`/`true`) | No |
| `jetpack_social_post_already_shared` | `bool` | No |

A defensive case also has to be handled regardless of which key: WordPress's own
`get_post_meta()` already unserializes a serialized meta value back into a PHP array before
returning it (`update_meta_cache()` runs `maybe_unserialize()` internally), so a well-formed
value always arrives as an array. If a value ever arrives as something other than an array (e.g.
a raw string — either genuinely malformed data, or a defensive fixture in the test suite), the
command **never** attempts to parse or `unserialize()` it itself; it is simply skipped, per rule 15.

## Mapping implemented

`SyndicationCommand::candidate_urls()` reads only `_publicize_done_external` (the one key that
can carry a URL) and maps Publicize's own service slugs to the three `ttm_syndication` networks:

- `twitter` → `x`, `x` → `x` (Jetpack renamed the service internally at different points; both
  slugs are accepted)
- `mastodon` → `mastodon`
- `bluesky` → `bluesky`

Any other service slug (e.g. `facebook`, `linkedin`, `tumblr`) is ignored — `ttm_syndication`'s
schema (SPEC §5.2) only has room for `x`/`mastodon`/`bluesky`. The first URL found per network is
kept; the whole candidate map is then run through the existing
`Meta\PostMeta::sanitize_syndication()` (already used by the REST/editor write path), which drops
anything that isn't a real `https` URL. A post that already has a non-empty `ttm_syndication`
value is left untouched — this command only fills gaps, it never overwrites editorial corrections.
`_wpas_done_*` and `jetpack_social_post_already_shared` are read nowhere in the implementation:
per the shapes above they cannot contribute a URL, so there is nothing for them to add.

## Limits

- Booleans-only keys (`_wpas_done_*`, `jetpack_social_post_already_shared`) are documented but
  inert; they exist in the codebase only as things the reviewer/owner should know were considered
  and ruled out, not as extraction sources.
- This spike could not be validated against a real WXR/Jetpack export (no live site access in
  this environment) — the shapes above come from Jetpack's own source, not an observed fixture.
- Only the first external URL per network is kept if Publicize recorded more than one connection
  to the same service (e.g. two different X accounts); `ttm_syndication`'s schema has one slot per
  network, so there is no way to keep more than one without a schema change.

## Follow-ups for the owner's real export

1. Run `wp ttm migrate:syndication --dry-run` against the real WXR import as the first thing
   after the WXR restore (before `convert:import`, which doesn't touch this meta) and check the
   row count against how many journal posts you actually remember sharing via Jetpack Social.
2. If `_publicize_done_external` turns out to be absent or empty on the real export (e.g. if the
   live site had Publicize's "keep URLs" option off, or predates that feature), the command will
   correctly do nothing — populate `ttm_syndication` by hand via the post sidebar for the posts
   that matter, per `docs/MIGRATION.md` §2.7.
3. If a real export surfaces a *different* shape for `_publicize_done_external` (e.g. a flat
   `{service: url}` without the connection-id nesting), `candidate_urls()`'s inner
   `is_array($entries)` check will simply skip that service rather than mis-parsing it — worth a
   quick manual audit (`wp post meta get <id> _publicize_done_external --format=json`) on a few
   real posts before trusting the dry-run count.
